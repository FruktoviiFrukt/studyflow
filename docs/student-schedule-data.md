# Структура БД расписания студента

Ветка: `feature/backend/student-schedule-page`. Реализован пункт 2: схема,
миграция и ограничения данных. API, импорт PDF и подключение страниц — следующие
этапы. Новых занятий или учебных периодов миграция не создаёт.

## Таблицы

| Модель                | Назначение                                                                |
| --------------------- | ------------------------------------------------------------------------- |
| AcademicYear          | Год, границы и понедельник первой нечётной недели                         |
| Semester              | Семестр 1/2, даты, ссылка на год                                          |
| StudyGroup / Subgroup | Группа и её подгруппы 1/2                                                 |
| Subject               | Название предмета и ключ цвета, без CSS-классов                           |
| ScheduleImport        | Расписание курса и семестра, даты действия, источник PDF, DRAFT/PUBLISHED |
| Lesson                | Недельное правило занятия: день, время, чётность, предмет и подробности   |
| LessonAudience        | Группы и подгруппы, для которых проводится занятие                        |
| ScheduleHoliday       | Один день или период без занятий для всего расписания                     |

`ScheduleImport` — одно редактируемое расписание. Версий, копий и архива нет.
`sourceFilename` — отображаемое имя, `sourceFileKey` — будущий ключ файлового
хранилища. Оба необязательны для ручного черновика. Сам PDF в БД не хранится.
Курс относится к расписанию конкретного семестра: его нельзя навсегда закреплять
за группой. Принадлежность пользователя пока текущая, без истории переводов.

## Регистрация и профиль: переходный контракт

- `User.group` сохранён для текущей регистрации и JWT. Удалять его пока нельзя.
- Миграция создаёт группы из существующих непустых значений, а также TI-245 и
  TI-246, создаёт для них подгруппы 1/2 и заполняет `User.groupId` по названию.
- `User.subgroupId` остаётся NULL: номер подгруппы пользователь выбирает сам.
- Оба ID необязательны для старых пользователей и администраторов.
- Составной внешний ключ запрещает выбирать подгруппу чужой группы.
- Это разовый перенос: регистрация после миграции пока пишет только `group`.
  При подключении профиля/регистрации нужно выбирать группу из справочника,
  записывать `groupId` и временно синхронизировать `group` в той же операции.
  Существующим пользователям без ID можно сопоставить группу по точному имени.
- При смене группы сбрасывать или одновременно менять подгруппу. Для доступа к
  личному расписанию сервер проверяет заполненность обоих ID и читает их из БД,
  а не полагается на старый JWT. Это предстоит реализовать в API.

## Правила расписания

- `weekday`: понедельник 0 — воскресенье 6.
- `startMinutes` / `endMinutes`: минуты от полуночи по Europe/Chisinau,
  например 18:45–20:15 = 1125–1215. Поддерживаются семь пар и другое время.
- Чётность: EVERY, ODD, EVEN. В PDF верхняя половина — ODD, нижняя — EVEN.
  Отсчёт идёт от `AcademicYear.firstOddWeekMonday`, включая каникулы,
  без сброса на втором семестре. Расчёт реализован в `lib/server/student-schedule.ts`; см. `student-schedule-calculation.md`.
- Даты периода — PostgreSQL DATE; границы включительны. В Prisma передавать
  даты через `new Date('2026-09-14T00:00:00Z')`, без местного сдвига времени.
- `LessonAudience.subgroupId = NULL` означает всю группу. Общая лекция — одна
  запись Lesson с несколькими получателями. Разные преподаватели/аудитории
  подгрупп — отдельные занятия. `teacher`, `classroom`, `topic` необязательны.
- Каникулы действуют на все группы и подгруппы этого расписания. Одинаковые
  начало и конец означают один день. Пересечения разрешены: день без занятий,
  если он входит хотя бы в один период. Недельные правила не удаляются.
- Удаление расписания каскадно удаляет его занятия, получателей и каникулы.
  Справочники и пользователей не удаляет. Используемые справочники защищены
  от удаления внешними ключами.

## Что проверяет БД, а что должен проверять будущий сервер

SQL-миграция добавляет CHECK для дней недели, времени, порядка дат, номера
семестра/подгруппы, положительного курса и понедельника отсчёта. Частичный
уникальный индекс запрещает дубли получателя «вся группа»; обычный уникальный
индекс запрещает дубли конкретной подгруппы. Эти SQL-ограничения нужно сохранять
в следующих миграциях: Prisma schema не выражает CHECK.

В API сохранения/публикации ещё нужно проверять: семестр внутри года, расписание
внутри семестра, каникулы в периоде расписания, непустые названия, наличие
получателей, отметку проверки, пересечения пар, одновременное назначение всей
группы и её подгруппы одному занятию. Публикация должна в транзакции исключать
два действующих расписания для тех же групп и дат. Само поле PUBLISHED этих
проверок не выполняет. Права ADMIN также проверяются сервером.

## Применение и проверка

После запуска Docker Desktop:

```sh
npm run db:up
npx prisma migrate deploy
npx prisma generate
npm run db:studio
```

Не использовать db:reset для применения этой миграции: существующие данные
нужно сохранить. В Studio проверить таблицы и перенос `User.groupId`;
пустые занятия ожидаемы.

Интеграционный тест: `tests/integration/schedule.test.mjs`. Запускать на отдельной
тестовой БД с применёнными миграциями, задав DATABASE_URL и ALLOW_DB_TESTS=1,
через `npm run test:db`. Тест создаёт только свои записи и удаляет их после
проверки. Проверка самого переноса старых групп требует базы на предыдущей
миграции и пользователя с заполненным строковым `group` до применения новой.

Админка, полуавтоматический импорт PDF, сохранение и публикация реализованы.
Актуальный запуск и ограничения описаны в `admin-schedule-import.md`.
Выбор группы/подгруппы в профиле остаётся отдельной задачей.
